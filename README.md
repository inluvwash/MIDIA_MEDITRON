«Мидия» — веб-сервис ИИ-скрининга анемии и латентных дефицитных состояний по числовым матрицам лабораторных анализов, разработанный для кейса Сеченовского университета.

Техническое написание: `MIDIA`. Смысловая расшифровка: Многослойная интеллектуальная диагностическая интерпретация анализов.

Слоган: «Мы не автоматизируем эмпатию — мы освобождаем для неё место».

## Цель решения

Сервис помогает врачу быстро интерпретировать совокупность лабораторных показателей, а не отдельные значения. Основной pipeline объединяет:

- прозрачные клинические правила;
- 12-классовую ML-классификацию;
- оценку неопределённости и следующий наиболее информативный маркер;
- причинно-следственное представление результата;
- похожие лабораторные профили;
- справочную подсказку по МКБ-10;
- отдельные PDF-отчёты для врача и пациента;
- опциональное локальное AI-пояснение.

LLM не является диагностическим движком: она не пересчитывает лабораторные значения, не меняет рассчитанный класс и не назначает лечение.

## Что реализовано

- Streamlit-интерфейс для врача (`HealthScreening.py`).
- FastAPI-интерфейс (`api.py`).
- Импорт одного пациента из текстовых PDF, TXT, CSV, TSV, JSON, XLSX, XLS и HTML.
- Ручной ввод и проверка лабораторных значений и единиц измерения.
- 7 слоёв результата: нормализация, клиническая логика, ML, неопределённость, причины, похожие профили, AI.
- 12 детальных классов анемии/дефицитных состояний.
- Локальная обезличенная база подтверждённых случаев.
- Локальный RAG по разрешённым PDF в `books/`.
- Отдельный врачебный PDF и лист пациента.
- Docker и Windows-скрипты для воспроизводимого запуска.
- Автоматические тесты.

### Финальный UX

- верхняя панель: «Справочник», «О проекте», «Инструменты», переключатель темы и «Новый пациент»;
- загрузка файлов оформлена русской кнопкой «Загрузка»; после выбора сохраняется карточка файла и доступна только кнопка удаления;
- аналогичная загрузка используется для локальных PDF в служебных инструментах;
- AI-пояснения формируются только на русском языке;
- в PDF обычный текст и таблицы — чёрные, заголовки — синие;
- синие и красные информационные рамки имеют одинаковую рабочую ширину, закруглённые углы и согласованные отступы;
- медицинское/ML-ядро при UX-правках не изменялось.

## Область применения и медицинские ограничения

Прототип предназначен для поддержки врача при скрининге совершеннолетних пациентов.

Ограничения:

- результат является рабочей скрининговой гипотезой, а не окончательным диагнозом;
- сервис не назначает препараты и дозировки;
- беременность находится вне области применения текущей версии;
- не предназначен для неотложных состояний;
- внешняя клиническая валидация на независимой репрезентативной выборке не проводилась;
- обучающий датасет частично синтетический, поэтому внутренние метрики не следует трактовать как доказанную клиническую эффективность.

## Быстрый запуск на Windows

Требуется установленный Python. Из корня проекта:

```powershell
.\scripts\start_windows.bat
```

После запуска откройте:

```text
http://127.0.0.1:8501
```

API при необходимости:

```powershell
.\scripts\start_api_windows.bat
```

Тесты:

```powershell
.\scripts\run_tests_windows.bat
```

Подробный краткий сценарий: `START_HERE.txt`.

## Запуск через Docker

Основной интерфейс:

```bash
docker compose up --build web
```

После запуска: `http://127.0.0.1:8501`.

API:

```bash
docker compose --profile api up --build
```

API будет доступен на `http://127.0.0.1:8000`.

Ollama не обязателен: clinical/ML/uncertainty/causal pipeline работает без него.

Настройки (адрес Ollama, API-ключ) можно задать файлом: скопируйте `config/.env.example` в `.env` в корне проекта (Docker) или в `config/.env` (локальный запуск). Подробнее — `config/README.md`.

## Как пользоваться

1. Указать ФИО пациента для текущего печатного отчёта, возраст и пол.
2. Заполнить жалобы / симптомы, анамнез и постоянные препараты.
3. Загрузить один лабораторный файл либо внести показатели вручную.
4. Проверить распознанные показатели и единицы измерения.
5. Выполнить скрининг.
6. Просмотреть семь слоёв результата.
7. При необходимости сформировать локальное AI-пояснение.
8. Скачать врачебный PDF и/или лист пациента.

## Входные данные

Поддерживаются:

- текстовые PDF;
- TXT;
- CSV / TSV;
- XLSX / XLS;
- JSON;
- HTML-таблицы;
- ручной ввод.

Текущая карточка предназначена для одного пациента. Многопациентские таблицы отклоняются. Сканированные PDF без текстового слоя требуют внешнего OCR и не входят в эту сборку.

ФИО не является ML-признаком и используется только для формирования текущего PDF.

## Выходные данные

Интерфейс показывает:

- ведущую скрининговую гипотезу;
- ключевые лабораторные факты;
- клинические правила и дополнительные направления проверки;
- ML-рейтинг классов;
- альтернативную гипотезу и карту неопределённости;
- наиболее информативный следующий маркер;
- причинно-следственные связи;
- похожие профили;
- справочные кандидаты МКБ-10;
- опциональное AI-пояснение.

Формируются два независимых документа:

- врачебный PDF;
- лист пациента.

## Архитектура

Основная логика находится в `screening/`:

- `schema.py` — контракт данных, нормализация, единицы и ограничения входа;
- `clinical.py` — прозрачные клинические правила;
- `ml.py` — 12-классовая Random Forest;
- `uncertainty.py` — top-2 неопределённость и value-of-information;
- `causal.py` — причинно-следственные связи;
- `similar.py` / `casebase.py` — похожие профили и локальная обезличенная база;
- `coding.py` — справочная логика МКБ-10;
- `rag.py` / `context_ai.py` — локальный AI/RAG;
- `report.py` — PDF-отчёты;
- `service.py` — оркестрация слоёв.

Точки входа:

- `HealthScreening.py` — Streamlit;
- `api.py` — FastAPI;
- `launch.py` — Python launcher.

Подробнее: `docs/ARCHITECTURE.md`, `docs/MODEL_CARD.md`.

## ML

Модель: `RandomForestClassifier`.

Вход: возраст, пол и лабораторные признаки. Целевые колонки датасета не используются как признаки.

Детальные классы:

1. `no_anemia_no_deficiency`
2. `latent_deficiency`
3. `iron_deficiency_anemia`
4. `B12_deficiency_anemia`
5. `B12_deficiency_no_anemia`
6. `folate_deficiency_anemia`
7. `folate_deficiency_no_anemia`
8. `B6_deficiency`
9. `copper_deficiency`
10. `inflammation_anemia`
11. `mixed_deficiency`
12. `anemia_other`

Внутренняя OOF-оценка на предоставленном датасете (840 записей):

- accuracy: `0.889`;
- balanced accuracy: `0.878`;
- macro F1: `0.885`;
- ECE top-score: `0.262`.

`Model score` используется как относительный рейтинг классов и не является вероятностью диагноза.

## Локальный AI

AI-слой опционален. По умолчанию:

```text
OLLAMA_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen2.5:7b
```

Настройки: `config/.env.example`.

AI получает уже рассчитанный обезличенный контекст и формирует русскоязычное пояснение. Основной скрининг не зависит от доступности LLM.

В текущем прототипе Ollama с моделью `qwen2.5:7b` используется как опциональная бесплатная локальная альтернатива внешнему LLM API. Основной clinical/ML/uncertainty/causal pipeline полностью работает без неё. Для первоначальной установки Ollama и загрузки модели требуется доступ к соответствующим внешним ресурсам; в отдельных сетевых окружениях доступ может быть ограничен, и при необходимости может использоваться VPN. В дальнейшем локальный генеративный слой может быть заменён или дополнен более быстрым API при условии соблюдения требований к защите медицинских данных.

## API

Основные endpoints:

- `GET /v1/schema`
- `POST /v1/predict`
- `POST /v1/import`
- `GET /v1/sources`
- `GET /v1/model-info`
- `POST /v1/report`

Опциональная защита API задаётся переменной `HEALTHSCREENING_API_KEY`.

## Персональные данные

Архитектура прототипа минимизирует использование ПДн:

- ФИО хранится только в текущем состоянии интерфейса;
- ФИО не передаётся в `screen()` и ML;
- ФИО не входит в JSON результата;
- ФИО не передаётся локальной LLM/RAG;
- локальная база подтверждённых случаев хранит обезличенные признаки и подтверждённую метку.

Сформированный PDF может содержать ФИО и должен храниться и передаваться по правилам медицинской организации.
