## Принцип

Система не строится вокруг одного «умного» алгоритма. Каждый слой имеет отдельную ответственность и может быть проверен независимо.

```text
Файл / ручной ввод
        │
        ▼
Нормализация + safety gate
        │
        ├── Клинические правила
        ├── ML: 12 классов
        │
        ▼
Согласование / явный конфликт
        │
        ├── Карта неопределённости
        ├── Сопутствующие сигналы
        ├── Причинные связи с анамнезом
        ├── Похожие профили reference cohort
        └── МКБ-10 reference-only
        │
        ▼
Врачебный интерфейс / PDF
        │
        └── Опциональный локальный LLM-редактор
```

## L0 — Identity isolation

ФИО существует отдельно от медицинского payload.

`HealthScreening.py` передаёт в `screen()` только обезличенные данные. ФИО передаётся непосредственно в `generate_pdf(..., patient_name=...)` и не входит в JSON результата, модель или RAG.

Это сокращает поверхность хранения персональных данных и позволяет врачу получить привычный подписываемый/печатный отчёт без создания локальной базы пациентов.

## L1 — Input + safety gate

`screening/importers.py`, `screening/schema.py`

- импорт одного пациента;
- многостраничный PDF объединяется в одну карточку;
- многопациентские таблицы отклоняются;
- все распознанные данные остаются редактируемыми;
- неизвестные единицы не используются молча;
- технически невозможные значения блокируются;
- возраст <18 блокируется;
- беременность блокируется как неподдерживаемый клинический профиль.

## L2 — Deterministic clinical layer

`screening/clinical.py`

Прозрачные правила:

- Hb и наличие анемии;
- железный обмен с поправкой на воспалительный контекст;
- B12 / MMA / активный B12 / гомоцистеин;
- фолаты;
- B6;
- медь;
- inflammatory pattern;
- mixed deficiency hints;
- альтернативные направления: почки, гемолиз, щитовидная железа.

Этот слой может поддержать или оспорить ML и не зависит от LLM.

## L3 — ML layer

`screening/ml.py`

Random Forest классифицирует только по 12 классам `anemia_class`. Симптомы, анамнез и препараты не являются входами модели, потому что их нет в обучающем наборе.

`predict_proba` отображается как Model score, не как клиническая вероятность.

## L4 — Uncertainty-first layer

`screening/uncertainty.py`

Ключевой продуктовый слой:

1. показывает ведущую и альтернативную гипотезы;
2. объясняет факторы неоднозначности;
3. оценивает недостающие маркеры;
4. выбирает один наиболее информативный следующий показатель в рамках настроенных правил/model perturbation.

Цель — не выдавать длинный список анализов, а показать врачу, какой вопрос остаётся нерешённым и какое измерение лучше всего его проясняет.

## L5 — Coexisting signals

`screening/service.py`

Конкурирующая гипотеза и сопутствующее состояние — разные вещи. Поэтому система отдельно формирует `coexisting_signals`:

- несколько одновременно положительных дефицитных сигналов;
- параллельные направления из alternative/exclusion layer.

Эти элементы не меняют class_code и не объявляются диагнозами.

## L6 — Causal reasoning layer

`screening/causal.py`

Форма представления:

```text
Что видим → Что это поддерживает → Что может объяснять
```

Свободный текст единого поля «Жалобы / симптомы», анамнез и лекарства участвуют именно здесь. Причина показывается только если в введённом врачом контексте найден соответствующий сигнал. Если сигнала нет — система пишет, что причина по доступным данным не определена.

Это causal reasoning/explanation layer, а не строгий causal inference и не цифровой двойник.

## L7 — Similar profiles

`screening/similar.py`

Поиск похожих профилей выполняется только по предоставленной reference-выборке. В интерфейсе не отображаются ID пациентов датасета. Показываются сходство, класс, причина в выборке, возраст/пол и объём пересечения лабораторных признаков.

Этот слой не используется как независимое клиническое доказательство.

## L8 — ICD-10 reference layer

`screening/coding.py`

МКБ-10 показывается как справка для врача. Автокодирования диагноза нет.

## L9 — RAG + local LLM editor

`screening/rag.py`

LLM получает:

- готовый final class;
- findings rules;
- uncertainty map;
- causal chains;
- обезличенный клинический контекст;
- выбранные RAG-фрагменты.

LLM не получает ФИО и не имеет права менять числа, класс, score или назначать лечение. Если Ollama отсутствует — используется детерминированное объяснение.

## L10 — Report / clinician communication

`screening/report.py`, `screening/communication.py`

Отчёт ориентирован на врачебное чтение:

1. карточка пациента;
2. жалобы / симптомы / анамнез / препараты;
3. исходные лабораторные показатели;
4. итог скрининга;
5. clinical layer;
6. ML;
7. uncertainty;
8. coexisting signals;
9. causal chains;
10. alternatives/exclusions;
11. МКБ-10;
12. похожие профили: локально подтверждённые + reference;
13. источники;
14. отдельная последняя страница-опора для объяснения пациенту.

Система не пытается имитировать эмпатию. Она делает данные понятными и наглядными, чтобы эмоциональную часть коммуникации оставлять врачу.


## Локальная база подтверждённых случаев

`screening/casebase.py` хранит только обезличенные лабораторные признаки, возраст, пол и подтверждённую врачом метку/МКБ-10. ФИО, жалобы, анамнез и препараты не сохраняются. Эта база нужна для retrieval похожих профилей и не переобучает Random Forest автоматически. Продольной истории визитов в проекте нет.

## Что намеренно удалено

- продольная локальная история;
- сохранение визитов;
- batch/patient matrix UI;
- 5-групповая проекция;
- отдельное поле кровопотерь;
- отдельный комментарий врача;
- patient-facing интерфейс.

Это сокращает surface area хакатонного прототипа и концентрирует демонстрацию на сильной диагностической архитектуре.

## Human-centered interaction layer 

Этот слой намеренно расположен после медицинского расчёта и не влияет на class_code/ML-score.

- `doctor_brief` — сжатие результата до короткого attention budget врача;
- `patient_conversation` — детерминированная визуализация уже рассчитанного результата: факты, относительный ML-рейтинг, неопределённость, следующий шаг и упрощённые причинные связи;
- conversation mode в UI — представление без ML-жаргона;
- patient sheet в PDF — понятная страница для совместного просмотра с врачом.

Архитектурный принцип: AI не симулирует эмпатию; он уменьшает информационный шум, чтобы человеческая часть контакта оставалась человеку.
